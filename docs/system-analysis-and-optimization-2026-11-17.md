**质检自进化系统分析与优化方向报告**

分析日期：2026-11-17。分析对象：当前本地 v2.7.0 工作区代码，包括上一轮增加的代表错例、正确对照、上下文提取和通用提示词跨规则回归能力。设计依据：用户提供的“3.3.6 智能体能力迭代”图片。

本报告基于源码审查和隔离的内存样例实验，不涉及真实客户数据评测，不将演示指标视为业务效果。本次仅新增报告，没有修改业务代码、线上配置或数据。文中的“已实现”“代码问题”“设计风险”“建议”分别表示现有能力、可从代码确认的问题、特定使用条件下的风险和待建设方案。

**一、总体判断。** 当前系统已经形成可用的离线规则优化循环，但与图片中的“人工经验转化为可复用智能体能力，并经过独立测评、审核、发布和反馈”的完整体系仍有差距。

当前核心优化对象是正则、语义描述和全局提示词；图片中的优化对象还包括专家知识、判断步骤、证据使用方法及业务处理边界。这意味着下一步需要同时解决三个问题：能否准确表达业务任务，能否可信地证明提升，能否把有效经验稳定地投入业务并持续积累。

建议首先修正评估与数据关联问题，再用“投诉意图识别与及时安抚”做一个完整能力包试点，最后扩展审核发布和生产反馈。增加迭代次数、扩大提示词或更换模型，均不应排在这些工作之前。

**二、对照图片的六个阶段。** 当前项目 README 明确将自己定位为简化实现，主动省略了审批、灰度、发布和回滚。因此，下表中的缺失既包括需要修正的问题，也包括从演示工具走向完整系统时需要补齐的范围。

| 图片中的环节 | 当前已实现 | 主要差距 | 判断 |
| --- | --- | --- | --- |
| 1. 初始化智能体与黄金案例反馈 | 规则配置，通话与人工标签导入，训练/验证/测试划分 | 标注只有规则级最终结果，缺少证据、角色、步骤、复核状态；知识没有独立资产结构 | 有数据入口，黄金案例体系不完整 |
| 2. 评分基线建立 | 正则和语义评测，准确率、精确率、召回率、F1，逐条结果 | 缺少证据与判断过程评分；基线没有完整不可变实验清单；失败样本可能退出计分分母 | 有结果基线，可信度仍需加强 |
| 3. 推演、反思与进化 | 最优版本的训练错例驱动；代表性取样、正确对照、修改计划、历史尝试 | 错因仍是模型假设；知识不独立积累；局部修改只靠提示词约束；每轮单一候选 | 核心循环已成立 |
| 4. 效果评估 | 验证集择优；改变全局模板时检查其他语义规则 | 选择主要依赖准确率；共享输入变更的回归范围不完整；缺少稳定性与业务约束 | 可比较版本，尚不足以证明业务收益 |
| 5. 独立测评、审核 | 每次任务末尾测试基线与候选；PASS/FAIL/INSUFFICIENT；应用理由 | 独立数据未封存；测试集可跨任务反复查看；没有独立审核角色及正式审批流程 | 有最终测试，尚非完整独立验收 |
| 6. 发布与反馈 | 应用到本地当前规则，记录版本、理由和修改历史 | 未见生产部署、影子运行、灰度、回滚、业务效果回流及复标队列 | 本地应用闭环，生产闭环待建设 |

**三、已有设计值得保留。** 当前实现中有几项正确的基础，不应在后续升级时推倒重来。

- 候选生成只使用训练样本，验证集负责选择，测试集在单次优化结束后评估，已具备基本职责划分。
- 误报、漏报分别取代表案例，并加入相似的正确案例，能帮助模型同时看到“应该扩展的边界”和“必须保留的边界”。
- 长通话优先保留命中或理由附近上下文，比固定截取开头更合理。
- 候选需要说明错误原因假设、保留行为及修改计划，迭代页面能展示这些信息。
- 通用提示词回归强制完成语义判定，对调用失败和原正确案例退步做了阻断；应用共享提示词前还检查上下文指纹。
- 修改理由、版本历史、请求重试、取消和调用日志，为后续审查及故障定位提供了基础。

这些能力分别属于“更有效地提出候选”和“限制修改影响”的第一步。现有分组是启发式线索，不是已确认的业务根因；模型给出的修改理由也不能直接当作能力提升的证据。

**四、首先要解决业务任务表达问题。** 图片中的案例并非单纯判断一句话有没有违规词，而是一个有角色、有顺序、有条件的任务：先识别客户是否表达投诉意图，再判断坐席是否在约定时间或话轮内做出合适回应，最后输出质检结论。

当前 `RuleInput` 的核心字段是 `regex / semantic / logic`；正则对整段转写执行搜索；语义用户提示词固定要求“只有坐席的行为满足条件才算违规，客户说的话不能单独作为违规依据”。默认系统提示词还要求只依据坐席发言。即使用户在界面修改通用提示词，用户提示词中的固定角色限制仍存在。

对于侮辱、威胁等坐席行为规则，这种限制有合理性；对于图片中的联合判断任务，它会形成语义冲突：客户发言是投诉触发条件的重要证据，必须进入判断。正则扫描全文又没有相同的角色限制，两个执行分支的口径也不一致。

建议把规则扩展为可配置的任务结构：

| 字段/组成 | 投诉安抚场景示例 | 作用 |
| --- | --- | --- |
| 判断对象与角色 | 客户意图、坐席回应、双方交互 | 按规则选择证据来源 |
| 触发条件 | 明示投诉，或对未经同意办理等事项表达不满并要求解释 | 不把普通咨询直接当投诉 |
| 所需回应 | 回应具体诉求、解释或处置、适当安抚 | 不把出现“放心”当作充分条件 |
| 时序条件 | 投诉发生之后的指定话轮/时间窗 | 区分此前寒暄与事后响应 |
| 例外与适用范围 | 引用他人投诉、已妥善处理、转写不完整等 | 明确边界 |
| 输出结构 | 各步骤结果、证据话轮、最终结论、待复核原因 | 支持诊断与复核 |

“及时”的具体窗口和“适当回应”的业务标准应由业务方定义，不能由优化模型自行发明。对于缺失后续对话的节选，系统应返回证据不足或待复核，不能仅因节选中没有安抚话术就认定违规。

对于这个场景，可以将最终逻辑表达为“确认有投诉意图，且未满足规定的回应要求”，同时明确未知状态的处理。简单关键词规则仍可以保留原执行方式，无需把所有规则升级成复杂流程。

**五、把专家经验建设成独立、可验证的知识资产。** 图片右侧的关键变化是增加了专家知识和判断步骤，而不只是增加投诉关键词。当前系统虽能把经验写入语义字段、修改说明和提示词历史，但没有独立的知识记录、作用范围、来源与批准状态。

建议为每条经过验证的经验记录以下内容：

- 经验内容，例如“质疑办理授权并表达不满，可构成间接投诉意图”。
- 适用业务和条件，例如该判断需要结合上下文，不能将所有疑问句都视为投诉。
- 排除条件与正确反例，例如仅询问流程且未表达不满。
- 来源案例、人工标注依据、证据话轮及复核人。
- 对应失败类型、预期改善点、回归案例和验证结果。
- 状态、版本、批准记录、冲突与替代关系。

演化模型先生成“候选经验”，经过事实核对、反例检验和评测后再变为“已批准经验”。有效经验可以关联多条规则；出现冲突时进行范围拆分或人工裁决。历史失败方案保留为实验记录，不能不加选择地塞进生产提示词。

建议将“规则定义 + 专家知识 + 执行步骤 + 提示词 + 回归案例 + 模型配置”作为一个能力包进行版本管理。初期采用结构化 JSON 和数据库即可，知识规模与检索需求达到一定程度后再引入检索系统。

**六、先让数据和评估结论可信。** 以下问题具有明确代码依据，部分已用内存构造样例复现。

| 问题 | 当前行为与影响 | 优化方向 | 优先级 |
| --- | --- | --- | --- |
| 未标注被当正常 | `cases_for_rule` 将人工规则列表中未出现的编号全部视为 NORMAL；若人工仅复核了部分规则，会制造假负样本 | 增加每条规则的复核状态；区分已确认正常、违规、未评审、无法判断；旧格式声明“已全量复核”才采用现有解释 | P0 |
| 规则编号与标签关联脆弱 | 编辑编号只更新规则并重建切分，不迁移通话中的编号标签 | 标签绑定稳定 ruleId，编号为可变业务属性；过渡期进行原子迁移和一致性校验 | P0 |
| 失败样本可能退出分母 | 语义失败比例不超过 10% 时可以返回结果；准确率只统计成功判定样本；普通优化验收不检查 coverage | 正式验收要求固定评价集合、完整覆盖；失败单列为未完成；探索性结果显示有效样本指标与全样本保守指标 | P0 |
| 准确率主导选优 | 验证准确率提高，或持平且训练准确率提高即可采纳；召回率/F1不作为主要约束 | 为投诉等高漏检成本任务配置召回底线、误报上限、关键场景约束及业务成本目标 | P0 |
| 极小样本可通过 | 验证、测试各一正一负即满足类别条件；没有证据量要求 | 同时检查关键类别与场景覆盖、样本量和统计不确定性；证据不足不能显示生产可用 | P0 |
| “达标”被描述成“提升” | 基线与候选均达标时，即使 improved=False，提升检查仍可通过，PASS理由声称有提升 | 拆分“达到可用门槛”“相对基线提升”“无需修改”三个结论 | P0 |

准确率的局限可以用一个假设例子说明：1,000 条通话只有 50 条投诉，全部判断为正常也有 95% 准确率，但投诉召回率为 0。图片目标是识别投诉并触发处理，单一准确率目标可能奖励错误的优化方向。

建议采用分层门槛：先满足数据完整性、证据覆盖和关键场景硬约束，再比较业务收益，最后比较成本、时延和复杂度。误报与漏报成本可以采用业务确认的权重，例如 `漏报成本 × FN + 误报成本 × FP + 人工复核成本`；不应让模型自行设置权重，也不应只凭训练集收益判定改进。

本次隔离实验结果如下，未调用外部模型，也未写入项目数据：

| 实验 | 实际观察 | 说明 |
| --- | --- | --- |
| 10 条不同通话，9 条正常判对，唯一违规样本模拟调用失败 | accuracy=1.0，coverage=0.9，recall=0.0，计分样本=9，errors=1 | 可同时出现“100%准确率”和关键样本未完成评测 |
| 验证与测试各一正一负，基线和候选均100%，improved=False | gate=PASS，理由仍写“相对基线有提升” | 达标与提升的展示和判定需要分开 |
| 构造12通话、两规则，按当前方式切分 | 4通电话在一个规则为TRAIN，在另一个为TEST | 共享能力优化时不能把这种划分视为全局隔离 |
| 同一构造数据中把R001改名为R101，不迁移人工编号 | 正样本数从6变为0 | 规则身份和标签关联需要稳定主键 |
| 仅修改一条规则的语义，通用模板保持不变 | 渲染后的系统提示词改变 | 回归触发条件不能仅比较模板文本 |

**七、让独立测试真正独立，并覆盖共享变更。** 当前每条规则分别分层切分，目的是让各规则尽量有正负样本，对单规则探索具有实用性。但全局提示词及全部语义规则会被共享，同一通电话可能已作为其他规则的训练材料进入共享能力优化，却又被当作独立测试材料。这是设计上的隔离风险，不能据此断言已经发生了真实业务指标污染。

建议对共享能力统一划分数据：以通话为基础，结合重复文本、同源对话、必要的客户/事件分组，避免相关样本跨集合。采用多标签分层尽量保证类别覆盖，稀有规则缺样本时明确标为证据不足，不通过重新拆散相关样本制造“可验收”。

每次实验固定 datasetVersion、splitVersion、标注版本、规则版本、提示词、知识版本、模型配置与可获得的模型版本、代码版本及采样清单。数据追加后创建新版本，历史结果仍能关联原输入；不能只有指纹而没有可恢复的内容。模型外部服务即使配置相同也可能存在波动，应记录运行时间和重复测量结果，避免承诺逐位复现。

开发验证集可以反复用于候选选择；正式独立测试集应按发布周期封存，并限制访问。单个任务末尾只测试一次，不能保证用户反复运行、查看结果、改方案后仍然独立。测试失败可以形成补充开发样本的需求，但不能将封存测试原文直接提供给生成器；反复调优后应安排新的独立验证数据。可增加时间外推样本，检验新的表达和业务变化。

共享变更还存在三个具体覆盖缺口：

1. 当前只有候选改变全局模板时才触发跨规则回归，但 `{rules}` 会注入全部语义规则。修改单条规则的语义或名称，也可能改变其他规则的系统提示词。
2. 手工保存全局提示词只校验内容和理由，不经过同一套回归门槛。
3. 当前应用前的上下文指纹检查主要约束全局提示词变化。纯规则结果应用时，仍应检查其评测基础是否被后续人工编辑或数据更新改变。

建议统一根据“实际执行输入及其依赖是否改变”决定回归范围，并让人工保存、批量导入、自动应用通过同一变更服务。必要时将只供当前规则使用的语义与共享知识分离，以减少跨规则影响。

现有“任何原本判对的样本都不得变错”很适合少量关键黄金案例。将它无差别用于所有普通案例，可能因模型波动阻断有净收益的变更。建议区分关键案例硬约束与普通样本的整体非退步要求，对差异样本重复评测；更宽松的策略必须有证据支持，不能直接取消保护。

**八、将验证职责与演化职责分开。** 当前系统并非没有验证：最终二分类指标是程序对照人工标签计算的，不是让大模型给自己随意打分。但 `judge_semantic` 承担的是执行规则并输出判定的职责，尚没有图片中针对证据和判断过程的独立验证模块；规则改写与执行还使用同一个模型客户端配置。

建议明确四个职责，初期可以保留在同一个应用中，不必立即拆微服务：

| 职责 | 输入与输出 | 核心限制 |
| --- | --- | --- |
| 质检执行 | 通话、能力包 → 分步骤结论、原文证据、最终结果 | 不修改规则和评分标准 |
| 验证评分 | 人工标准、执行结果 → 各维度差异、评分与错误定位 | 评分口径固定并版本化，不能由演化候选一起改写 |
| 演化生成 | 训练错误报告、已批准知识、历史实验 → 修改假设和候选补丁 | 不接触封存测试内容，不自行批准经验或发布 |
| 独立测评 | 冻结能力包、封存数据 → 可复核验收报告 | 数据、版本及权限独立于开发选择过程 |

验证至少覆盖：最终命中是否正确、客户意图是否识别正确、坐席回应是否符合要求、证据是否真实存在且角色正确、前后时序是否成立、最终结论能否由这些结果支持。

证据验证应优先使用程序核对话轮、原文片段和偏移；语义适配可由独立评审提示词或不同模型辅助，并通过人工标定检查一致性。不同模型不自动等于独立可信，同一模型也不意味着整个评测没有价值，关键是数据隔离、固定标准和人工校准。验证对象应是可核对的结果与证据，无需收集冗长的模型内部推理。

训练集目前要求输出理由，验证/测试只要求布尔结果，这会改变实际请求形式。建议统一生产和评测的判定结构，将额外诊断解释放在判定之后生成，并检查两者一致性，避免把不同执行条件的差异误认为数据泛化差异。

**九、把“错误驱动改写”升级为可检验的实验。** 当前每轮一个候选、根据当前最优规则继续搜索，易于解释和控制成本。建议保留这个主干，优先增强错误诊断和候选检验，再考虑多候选搜索。

建议的单轮流程为：

1. 按业务失败原因定位错误：投诉意图漏识别、角色归属错误、回应充分性错误、时序错误、上下文缺失、标注争议、模型调用失败等。调用失败进入可靠性修复，标注争议进入复核，不能都转化为改规则需求。
2. 将一个代表错例与一个相似正确反例配对，注明两者区别；当前字符串相似度与线索分组可作为初筛。
3. 输出可验证假设，例如“当前依赖显式投诉词，因此漏掉质疑办理授权的间接投诉”。假设关联案例、人工证据和需要保持的边界。
4. 生成结构化补丁，明确修改知识、正则、语义、步骤或共享提示词中的哪一项，以及影响范围。优先低影响范围修改，有证据时才调整共享内容。
5. 先做结构和执行检查，包括字段、正则方言、性能预算、不可变业务要求及新增知识冲突；无效候选在本轮修复或拒绝，不使整项优化无必要地失败。
6. 运行训练反例、关键回归和开发验证，按业务约束选优；必要时做单项消融，判断收益来自哪项改动。
7. 保存假设是否得到支持、哪些错误修复、哪些正确样本受损及新增调用成本；有效经验进入待审核知识记录。

当训练集已经没有错误，但验证集未达标时，应提示“当前训练证据不足以支持继续修改”，转向补充训练覆盖或更换训练抽样。不能把验证原文交给生成器，也不应盲目循环。增加重复候选去重、连续无改善停止、最大调用/费用预算、无效候选有限重试，可以减少无效消耗。

数据充足后，可在固定预算内探索少量不同假设，例如“只补知识”“只改判定步骤”“只调正则”，在开发验证集上比较。候选越多，越需要控制验证集被过度选择的问题；多候选本身不保证收益。

**十、长通话要按完整事件链取证。** 当前上下文提取已优先寻找证据锚点，但仍受1200字优化上下文和6000字语义输入上限约束；启发式窗口最多围绕少数锚点，可能保留投诉触发而遗漏较远处的处理回应。

建议将转写解析为带角色、时间、话轮ID的结构，先定位触发事件，再按业务窗口补齐回应及必要上下文。所有节选保留原文引用关系和省略范围，无法确认窗口完整时返回“无法判断”。对于否定性结论，如“没有安抚”，尤其需要证明应检查的后续范围已覆盖。

不要单凭模型生成的理由决定后续所有取样，否则模型看错证据后会持续把优化引向同一片段。人工标注的证据、规则触发位置、相关话轮检索应共同参与，最后由程序验证引用。

**十一、补齐审核、发布和反馈。** “应用为当前规则”目前是在本地写回配置，无法替代图中的人工审核与生产发布。

建议形成以下最小生命周期：草稿 → 开发验证通过 → 冻结候选 → 独立测评 → 人工审核 → 影子运行 → 小范围发布 → 正式发布；任一阶段可驳回，已发布版本可回滚。

审核材料应同时包含业务改动、能力包差异、代表性修复与退步案例、分场景结果、证据量、覆盖率、独立测试结论、延迟与成本。审批绑定确切版本；审核后内容变化应使原审批失效。当前本地“强制应用”可继续作为实验入口，但不得等同于正式发布资格。

生产反馈应保留实际使用的能力包版本和执行证据，并收集人工确认的误报、漏报、待复核原因、安抚或转人工情况。经去重、脱敏和复核后进入后续数据版本；不能把上一版模型自己的预测直接当作人工真值。

若声称能够“及时干预”，还需要接入通话中事件、告警或业务操作链路，并测量触发时延。当前系统处理已有文本，能支持事后质检和规则优化，代码不能证明已具备实时干预能力。客户体验或处理率的改善也需要在影子/试点阶段验证，不能从离线命中率直接推出。

**十二、工程和使用体验应随试点同步加强。** 当前 FastAPI、原生页面、单进程任务和 JSON 原子写入适合本地工作台。单用户阶段无需为了架构完整而引入大量服务；多人试点与生产接入时，以下边界会成为实际限制。

| 方向 | 当前情况 | 建议 |
| --- | --- | --- |
| 任务可靠性 | 活跃任务在进程内存中，重启不能从评测断点继续 | 持久化任务状态、分阶段检查点、幂等重试；单机可先采用SQLite |
| 数据与版本 | 全量JSON快照，保留有限运行记录 | 结构化存储实验/能力包，保留可恢复快照；多人写入时再选支持事务的共享数据库 |
| 并发与成本 | 模型单发串行，有重试和调用统计 | 增加运行前预算、token/费用记录、受限并发和速率控制；缓存绑定实际依赖；先测量再提并发 |
| 正则执行 | Python re全文匹配，只校验能否编译 | 按生产引擎验证方言；对候选增加时间预算及安全执行机制，防止复杂模式阻塞任务 |
| 数据访问 | 无登录与审批；请求/响应原文落日志；固定自定义鉴权值可持久化 | 多人或真实数据试点前配置身份权限、密钥引用、日志脱敏与保留范围；这是代码中具体数据流带来的要求 |
| 模式表达 | mock主要演示正则优化，不进行真实语义评估 | 显著标明模拟结果与真实评测，避免演示分数被当作上线依据 |
| 报告体验 | 已有迭代卡片、修改理由和逐条结果 | 增加“修复了什么/损失了什么”、证据完整性、标注争议、分场景漏报，以及候选状态与部署状态的区分 |

调用预算不能只用“样本数 × 轮次”估算：还应包括基线、每轮训练与验证、候选生成、跨规则回归、最终测试及失败重试，并扣除实际缓存命中。建议界面显示估算范围和实时累计，而不是给出容易低估的单一数字。

前端可围绕五个业务对象组织：数据与标注、能力配置、实验与错误诊断、独立验收与审核、版本发布与反馈。保留现有简洁入口，按阶段逐步开放高级功能。

**十三、实施顺序与验收标准。** 以下按依赖关系排序，工作量是相对判断，尚未据团队人数与真实数据规模估算日历工期。

| 阶段 | 建议工作包 | 预期收益 | 依赖/相对工作量 | 验收标准 |
| --- | --- | --- | --- | --- |
| P0：修正可信度基础 | 稳定规则身份；显式复核状态；完整覆盖门槛；业务指标选优；达标/提升分离；所有变更的依赖与过期检查 | 避免优化错误标签或发布无充分证据的结果 | 不依赖新模型，中等 | 编号调整不丢标签；未评审不算正常；失败样本不能悄悄退出正式验收；旧结果不能覆盖新版本 |
| P0：固定数据边界 | 统一分组切分；数据与实验版本化；冻结独立验收集 | 提高跨规则与跨轮次评估可信度 | 与数据格式升级联动，中等 | 同源样本不跨独立边界；历史实验可定位完整输入；生成器无法读取封存测试原文 |
| P1：投诉场景能力包 | 角色/话轮结构；投诉与回应分步判定；证据输出；知识记录与审核 | 直接对齐图片的业务能力 | 需要业务标准与分步黄金标注，中到大 | 覆盖隐含投诉、已适当回应、无关安抚、延迟回应、引用投诉、截断对话等关键案例 |
| P1：验证与演化 | 固定评分维度；结构化错因与补丁；反例回归；去重/早停/预算 | 能解释收益来源并减少无效迭代 | 依赖前两阶段，中等 | 每项采纳修改有可核对证据；关键正确边界受保护；无法归因时不自动批准知识 |
| P2：受控试点闭环 | 冻结验收、审核、影子、灰度、回滚；任务持久化与访问控制 | 将离线能力安全转入实际业务 | 需要生产接口及责任人，较大 | 审核与发布版本一致；可回滚；线上错误回流后形成经复核的新数据版本 |

下一次开发建议先落地P0，不同时重构整套架构。随后只选择“投诉意图识别与及时安抚”一个场景，采集足以覆盖关键边界的人工案例，以真实模型完成从错误诊断、知识生成到独立验收的端到端验证。样本数量应由类别稀缺程度、场景覆盖和指标不确定性决定，不宜用“几十条即可”作为通用承诺。

建议用四组结果衡量后续投入是否有效：关键漏报与误报是否改善；证据和步骤是否更可靠；复核工作量及单次评测成本是否下降；新时间段、新表达及其他规则是否保持效果。这些指标通过之前，不把“提示词变长”“迭代轮数更多”当作系统能力增长。
